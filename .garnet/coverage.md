# How much of this CI is covered

The honest answer is per job, from one real run of this repository's pull-request
CI, with the runner each job asked for. Three limits decide the number, and one of
them is a live defect rather than a boundary:

- The sensor is eBPF, so it records on Linux. macOS and Windows jobs are out of
  reach, and no amount of configuration changes that.
- A job records only if it carries the sensor step. That is a line of YAML, so
  every uninstrumented Linux job below is a choice, not a limit.
- A job that carries the step still records nothing if the sensor service fails to
  start. On the run below that happened in 7 of the 11 instrumented hosted-Linux
  jobs: the agent registered, `systemctl start jibril.service` failed about eleven
  seconds in, and the step warned that the workflow would continue without runtime
  monitoring. Those jobs ran; nothing recorded them. See
  [the sensor-start failures](#the-sensor-start-failures).

## What the ledger says

33 jobs ran or were scheduled. 4 recorded, and their 66 actions are the whole
evidence base for this commit: `cargo-deny` 36, `python-sdk-install` 18, `garnet`
8, `codespell` 4.

Of the 29 that did not record:

- **10 never acquired a runner.** They ask for this repository's self-hosted
  `codex-linux-x64` and `codex-windows-x64` groups, which the fork cannot reach.
  Nothing ran, so there is nothing to record — this is not a coverage gap.
- **7 carried the sensor and lost it to a failed service start.** This is the one
  number in this document that should be fixed rather than explained.
- **5 are macOS.** Outside an eBPF sensor's reach entirely.
- **7 are hosted Linux without the step**: the four Bazel Linux cells, the Windows-
  targeted Bazel cell that runs on Linux, and the two aggregator jobs that only
  collect other jobs' results. The Bazel cells are the real remaining gap.

So on hosted Linux, where the sensor can work at all: 18 jobs, 4 recorded, 7 lost
to the start failure, 7 not instrumented. The honest coverage claim today is
"4 of 18 hosted-Linux jobs", and the reachable claim once the start failure is
fixed and the Bazel cells carry the step is 18 of 18.

## The sensor-start failures

All 11 instrumented hosted-Linux jobs registered an agent with the API on this
run. 7 then failed at `systemctl start jibril.service` and the step warned:
`Jibril service failed to start. The workflow will continue without runtime
monitoring for this run.` The same 4 jobs recorded on both runs of this commit,
and the same jobs failed on both.

What was ruled out by probing it directly, in [PR #20][diag] (all probes started
the sensor successfully):

| probe | result |
| --- | --- |
| sensor `v2.15.0`, `v2.16.0`, `latest` | all started |
| `ubuntu-24.04` and `ubuntu-latest` runners | all started |
| full `fetch-depth: 0` checkout before the step | started |
| 12 jobs registering agents concurrently in one run | all 12 started |
| `pull_request`-triggered run on a merge ref | all started |

The cause is therefore not the sensor version, the runner image, the checkout, the
registration concurrency or the trigger. It is unresolved. The step logs no reason
for the failure — it does not capture `journalctl -u jibril.service` — which is
why this took five probes rather than one log line, and is the first thing worth
changing.

[diag]: https://github.com/garnet-labs/codex/pull/20

## The Bazel matrix

The five hosted-Linux Bazel jobs are the remaining Linux gap. They take the same
three lines as every other job. They were left out of this change because they are
the longest-running jobs in the repository, and the sensor's profile is flushed at
job end, so they are the jobs where instrumenting changes the most about how a
failure would be read. That is a sequencing decision, not a capability limit.

## macOS and Windows

The `Argument comment lint` job runs the same lint on Linux, macOS and Windows.
Only the Linux cell carries the sensor, and on this run it is one of the seven that
lost it to the failed service start, so there is no recording of it yet. The point
of instrumenting that cell stands: the same lint, the same toolchain, the same
destinations, run on the platform the sensor can read. It is the closest available
reading of what the macOS and Windows cells do, and it is a Linux recording. It is
not evidence about macOS or Windows behaviour, and nothing in this directory should
be read as such.

The self-hosted Windows and Linux jobs in this fork never acquire a runner, so
they report no steps at all. They are listed in the ledger as `no runner` rather
than as coverage gaps, because nothing ran to record.

## Jobs in the evidence that no longer exist

One job name appears in the evidence and not in the current workflows: `general`,
from one April 2026 commit of `blocking-ci`. Its recording is kept rather than
filtered out, because it is what the runner did on the commit where it ran. The
evidence file's five job names are therefore `cargo-deny`, `garnet`,
`python-sdk-install`, `codespell` and `general`.

The `Python SDK dependency install` job is the one job in the ledger that this
change added rather than instrumented. This repository's own Python SDK lane runs
on a self-hosted runner the fork cannot reach, so it never starts; the added job
runs the same `uv sync` on a hosted runner so the dependency install has a
recording at all. It is a hosted stand-in for a self-hosted lane, not an extra
check.
